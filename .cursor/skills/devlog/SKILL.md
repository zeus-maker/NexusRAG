# Devlog 技能

## 何时执行

在本仓库**修改代码或项目配置**且任务收尾时**必须**执行，除非用户明确禁止写 devlog 或禁止提交。

## 文件与编号

1. 路径：`docs/devlog/YYYY-MM-DD-修改点.md`（真实公历日期）。
2. **同日追加**到已有文件；**跨日新建**文件。
3. 追加前先读全文，取最大 `## N.` 的 **N**，新条目用 **N+1**。
4. 标题格式：`## N. 简短标题`。

## 质量标准

读者**只看 Devlog** 就应理解：改了什么、为何如此、如何验证、边界在哪。信息量与向用户收尾说明**同一档次**，略紧凑。

- **对齐交付**：对话里写清的根因、取舍、架构入口、运维注意点，Devlog 须有对应叙述。
- **结论先行**：开篇 3～8 句完整中文：现象/动机、目标状态、**用户可见变化**（无则写明）。
- **摘要要有语义**：写行为与契约，禁止「优化了 xx」「修复问题」空话。
- **验证可执行**：命令、页面路径、关键断言；「自测通过」须写测了什么。
- **反思非摆设**：有分支取舍、非显然约束、技术债时必选。

### 禁止

- 仅有涉及文件列表、摘要为空。
- 与 commit 正文完全重复且无技术语义增量。

## 正文结构（按任务删减，「涉及文件」不得顶替摘要）

1. **背景与目标**
2. **改动摘要**
3. **验证与风险**
4. **反思与沉淀**（复杂改动必选）
5. **涉及文件**（路径 — 一句用途）

## 硬性流程

1. 撰写/追加 Devlog 条目。
2. `git add`（含 devlog 与本次改动）。
3. `git commit`：中文 subject + body 分条，与 Devlog **同一信息粒度**。

## 模板

```markdown
## N. 标题

### 背景与目标

（3～8 句：动机、目标、用户可见变化）

### 改动摘要

- …

### 验证与风险

- 验证：…
- 风险/回滚：…

### 反思与沉淀

- …

### 涉及文件

- `path` — 用途
```
