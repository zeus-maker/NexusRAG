# Devlog 技能

## 何时执行

在本仓库**修改代码或项目配置**且任务收尾时**必须**执行，除非用户明确禁止写 devlog 或禁止提交。

## 文件与编号

### 写前必做（防止误追加到旧日文件）

1. **取当日日期**：执行 `date +%Y-%m-%d`（或读 user_info 中的 Today），记为 `TODAY`。**禁止**凭「最近改过的 devlog」猜日期。
2. **选目标文件**：`docs/devlog/TODAY-<主题>.md`（主题与任务一致，如 `rag3-frontend`、`backend`）。
3. **跨日必新建**：若不存在 `TODAY` 前缀的文件 → **新建**，条目从 `## 1.` 起；文首可加一行 `> 接续 YYYY-MM-DD-主题.md §N` 说明上下文。
4. **同日才追加**：仅当文件名日期前缀 **等于** `TODAY` 时，才在已有文件末尾追加；编号只在该文件内递增。
5. **禁止跨日追加**：不得向 `TODAY` 之外的 devlog 文件写入新条目（历史文件只读，用于查编号或写「接续」引用）。

### 编号规则

- 每个 devlog **文件**内独立编号：`## 1.`、`## 2.` …
- 追加前只读**当日目标文件**全文，取最大 `## N.` 的 N，新条目用 N+1。
- **不要**去旧日文件里取最大 N 再写到新文件（这是常见误操作来源）。

### 体量控制（建议）

单日单文件若已超过 **约 800 行** 或 **15 条**，优先新开 `TODAY-<主题>-b.md`（或按子域拆分主题），避免单文件难以检索与 diff。

### 命名示例

```
docs/devlog/2026-06-08-rag3-frontend.md
docs/devlog/2026-06-10-rag3-frontend.md
```

## 质量标准

读者**只看 Devlog** 就应理解：改了什么、为何如此、如何验证、边界在哪。信息量与向用户收尾说明**同一档次**，略紧凑。

- **对齐交付**：对话里写清的根因、取舍、架构入口、运维注意点，Devlog 须有对应叙述。
- **结论先行**：开篇 3～8 句完整中文：现象/动机、目标状态、**用户可见变化**（无则写明）。
- **摘要要有语义**：写行为与契约，禁止「优化了 xx」「修复问题」空话。
- **验证可执行**：命令、页面路径、关键断言；「自测通过」须写测了什么。
- **反思非摆设**：有分支取舍、非显然约束、技术债时必选。

### 禁止

- 仅有涉及文件列表、摘要为空。
- 与 commit 正文完全重复且无技术语义增量。
- 跨日历日仍往旧 `YYYY-MM-DD-*.md` 追加（即使该文件里 § 编号更大）。

## 正文结构（按任务删减，「涉及文件」不得顶替摘要）

1. **背景与目标**
2. **改动摘要**
3. **验证与风险**
4. **反思与沉淀**（复杂改动必选）
5. **涉及文件**（路径 — 一句用途）

## 硬性流程

1. `date +%Y-%m-%d` → 确定 `TODAY` 与目标文件路径。
2. 撰写/追加 Devlog 条目（遵守上文文件与编号规则）。
3. `git add`（含 devlog 与本次改动）。
4. `git commit`：中文 subject + body 分条，与 Devlog **同一信息粒度**。

## 写前检查清单

- [ ] 已执行 `date +%Y-%m-%d`，目标文件日期前缀 = 当日
- [ ] 跨日任务使用的是**新建**文件，而非最近打开的 devlog
- [ ] 编号仅在**当日目标文件**内递增
- [ ] 条目含可复现验证与用户可见变化
